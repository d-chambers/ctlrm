# Reusable workflows

`ctlrm workflow validate --template workflow.yaml` validates a version 1 template. Templates define named profiles, roles, an entry task, explicit outcome transitions, and a bounded number of executions. Use `tasks` for fixed generic task definitions, each with its own `instructions` and assigned `role`. A job supplies the goal shared by those tasks; each visit creates a separate task execution, while session recovery continues that execution. Templates use schema version 1 with one canonical representation: `tasks`, `job_id`, and task executions that identify their `task`. `profiles` maps names to the provider profiles described in [managed sessions](managed-sessions.md). Human roles have no profile. A terminal destination is `terminal:completed`, `terminal:rejected`, or `terminal:failed`.

Submit with `ctlrm --root WORKTREE workflow submit --template workflow.yaml --title "Job" --file job.md --request-id SUBMISSION_ID`. Every role defaults to a participant with the same name; repeated `--bind ROLE=PARTICIPANT` options may supply a complete alternative binding. Reusing a submission ID with identical inputs retries initialization. A different job requires another worktree. Direct submissions without change-size thresholds can initialize an unborn branch; commit its initial code before reporting an outcome. Central jobs and size-triggered templates require a committed base revision. The template, profiles, job, and bindings are immutable snapshots; later changes to the source template cannot change the run.

`workflow status` exposes run progress, execution history, session state, and diagnostics. Each assignment records an execution ID and exact acknowledgment/report commands. Agents and humans must acknowledge before acting and report an explicitly allowed outcome. Humans first accept their assigned role with `workflow join --participant NAME`. `workflow report` is also the human-response command. A rejected stale or unknown outcome remains visible in request history and cannot advance the job.

Each review-loop visit has a new execution ID and carries the previous summary. Accepted transitions and assigned mailbox IDs survive supervisor restart; publication and terminal hints may repeat, while the logical assignment does not. Human approval is independent of provider tool permissions. The supervisor validates all profiles before submission, launches the active agent role lazily, and reuses healthy sessions across visits. Explicitly stopped sessions stay stopped until resumed or replaced.

The coordination area is cooperative, writable by the same operating-system user. Role signatures validate workflow identity and intent; they do not authenticate a human against another process with the same filesystem access. Managed agent environments are prevented from calling human response operations as an accidental role crossing, but a malicious same-user process can remove that environment marker or alter files. Use a separately authenticated service for security-sensitive approvals; that is outside this local runtime.

The event journal records immutable state deltas from the first event, keeping existing execution history and request results out of new record sizes. Immutable records remain bounded to 8 MiB each.

Each outcome captures an immutable artifact manifest under `.ctlrm/artifacts/`, recording HEAD, dirty status, a Git index digest, and content hashes for tracked and non-ignored untracked files. Runtime files are excluded. Symlinks record link text without reading their targets. Clean nested Git repositories/submodules record their commit; dirty nested repositories require committing their changes before handoff. Capture is bounded to 10,000 files and 64 MiB. Assignments name the input artifact, which acknowledgment and report commands must repeat with `--input-artifact`. Each template task must explicitly set `verify_input`: use `true` for review/approval tasks and `false` for implementation tasks that intentionally change the input. A task with `verify_input: true` checks every outcome against that version, regardless of its name; changed content leaves the execution active with a rejected request. These checks detect changes at observation time and cannot prevent concurrent manual writes after inspection.

`workflow cancel` commits cancellation before stopping every owned agent, including while branch drift has paused dispatch. `workflow retry --execution-id ID --reason TEXT` explicitly abandons a visit and creates a new one within the template's execution limit. Stop its agent first, retry, then use `session resume` or `session replace`. Retry refreshes any input artifact against the current worktree, making a new review acknowledgment necessary. Native recovery retains the execution ID but requires reconciliation and current-generation acknowledgment before an outcome. A generic session completion cannot bypass workflow outcome validation.

Codex defaults to a terminal-owned `codex exec --json` turn runner, using `exec resume` for further native turns. Generation-specific immutable input hints wake it without typing into a provider permission dialog. This uses Codex's configured permissions and credentials. Claude interactive automation still requires an explicit unattended profile; its default profile is manual. Managed agent reports do not silently restart an explicitly stopped supervisor; restart it with `supervisor start` to accept pending requests.

A runnable [implement/review/approval template](../examples/implement-review.yaml) uses two independent Codex sessions with one shared profile definition. Output intended for handoff must be tracked or non-ignored; add intentionally ignored output to Git before reporting it so its version is included. The [mixed-provider acceptance record](evidence/mixed-workflow-2026-09-05.json) demonstrates Codex implementation, Claude review, native interruption/recovery, requested changes, supervisor restart at a pending handoff, the human response API, and isolated reuse of an unchanged template.

Retry inputs explicitly identify the abandoned execution that was recaptured and retain the previous artifact reference; they do not attribute edited content to the original producer.

Native bootstrap turns that finish without accepted readiness are redelivered at a bounded interval while startup is still allowed. The registration timeout remains the upper bound; visible blocked startup requires explicit intervention. A failed native turn exits the runner and enters generation recovery rather than blindly repeating a turn that may already have performed effects.

For a task whose outcomes have different verification requirements, set `verify_input: false` and list the checked transition names in `verified_outcomes`. Those names must exist in the task's transitions.

## Bounded specialist tasks

Optional tasks remain fixed in the YAML graph. Mark a specialist task `optional: true`, assign its role and instructions, require `verify_input: true`, and declare exactly `approved: terminal:return` and `changes_requested: FIX_TASK`. Optional tasks cannot request more specialists. A normal review task declares its `specialist_tasks` allowlist and an `approved` outcome. Its accepted approved report may include repeated `--specialist TASK` flags and a bounded `--specialist-reason`. The supervisor validates the request before accepting the report and records the requester, reason, input artifact, pending specialists, and normal continuation.

Specialists run sequentially. Approval proceeds to the next requested specialist, then resumes the normal graph. Findings route to the specialist's declared fix task and supersede remaining reviews of that version. Summaries and artifact references travel with the handoff. Retrying a specialist after the worktree changes invalidates the prior review chain and returns to its fix task; earlier approvals cannot authorize the changed version. After approval returns to the normal graph, a changed-version retry of an input-verifying task is rejected when it would invalidate recorded approvals. Tasks that deliberately mutate input can retry their unfinished implementation. Restore the reviewed version and use the workflow's fix outcome, or cancel and start a new job. `limits.max_specialist_executions` bounds specialist executions over the whole job; `max_executions` on an individual task bounds all of its visits and retries. Exhausted limits never silently skip required review. An automatic review that cannot start within the remaining budget leaves the job visibly blocked with its limit reason. Over-budget discretionary requests are rejected before accepting the report.

A requester may declare `specialist_above_lines: {review_performance: 100}` to activate a permitted task when tracked additions plus deletions exceed the threshold relative to the job's initial HEAD. This is a heuristic for tracked text changes; binary and untracked files need reviewer judgment. The allowlist and global budget still apply. `fresh_session: true` stops an earlier owned session before replacing its conversation for a new task execution. Explicit retries also start a fresh conversation. Native recovery during that execution continues the same conversation and execution.

`requires_pr` lists outcomes that require structured PR metadata. Report with `--pr-number N --pr-repository OWNER/REPO` and optional `--pr-url URL`. Accepted metadata becomes searchable through `job find`; an explicit `job assign-pr` correction takes precedence. PR reporting does not grant an agent write access to other project jobs.

The [ship template](../examples/ship.yaml) defines implementation/check/commit, blast-radius review, optional performance/concurrency specialists, fresh counterpart review, PR publication, and CI/review-thread handling, including an open, mergeable PR check. It stops at merge-ready and bounds implementation to the initial visit plus three fix rounds. It follows repository instructions and does not weaken checks or merge automatically. Git hosting commands are performed by the assigned agent using its configured tools and credentials; ctlrm records the outcomes rather than independently authenticating their truth.

The ship template's Claude profile retains manual input by default. Configure an explicitly unattended Claude profile with `--permission-mode dontAsk` and your chosen permitted tools to automate terminal delivery; do not use policies that allow Enter hints to approve dialogs. A reviewer that is unavailable must report that outcome, which fails this example job rather than fabricating approval. Customize this policy in your source template before planning a job. The [single-agent template](../examples/single-agent.yaml) uses one fixed task and one managed Codex conversation.
